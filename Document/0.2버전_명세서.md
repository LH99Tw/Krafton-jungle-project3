## 0. 문서 목적과 상태 표기

0.2는 0.1 피드백을 실제 3인 멀티플레이 구조에 맞게 구체화한 버전이다. 기존 Phaser 로컬 수직 슬라이스의 규칙을 그대로 복제하지 않고, Node.js·Colyseus·PostgreSQL 환경에서 서버가 최종 판정을 소유하도록 이전한다.

이 문서에서는 구현 상태를 다음과 같이 구분한다.

| 표기 | 의미 |
|---|---|
| **구현 완료** | 코드와 자동 테스트가 존재하며 현재 저장소에서 검증됨 |
| **부분 구현** | 기본 end-to-end 경로는 동작하지만 관련 효과·UI·고급 규칙 또는 실제 다중 클라이언트 검증이 남음 |
| **미구현** | schema 또는 기획만 있고 실제 서버 판정/클라이언트 표현이 없음 |
| **운영 검증 필요** | 코드 경로는 있으나 실제 인증·배포·부하 환경 검증이 남음 |
| **결정 필요** | 대안 중 최종 선택 또는 수치 확정이 필요함 |

우선순위는 본 문서 > `0.1버전_명세서.md` > `0.1버전_밸런스_데이터.md` > 원본 수정사항 순이다. 0.2에서 명시하지 않은 0.1 규칙은 계속 유효하다.

## 1. 0.2 목표

1. 솔로 1명 또는 실제 사용자 3명이 같은 서버 권위 게임을 플레이한다.
2. AI 동료 없이 구역1 → 구역2 → 구역3 → 최종 보스로 진행한다.
3. 각 구역은 5×5 논리 그리드와 정확히 15개의 연결된 방을 가진다.
4. 자동 공격, 적 AI, 웨이포인트, 성장, 드롭, 건설, 승패를 서버가 판정한다.
5. 같은 seed와 같은 명령 순서는 같은 맵·드롭·증강 결과를 만든다.
6. 링크로 접근한 테스트 사용자가 실제 배포 환경에서 한 런을 완료할 수 있다.

## 2. 플레이어와 파티

### 2.1 확정 모드

| `partyMode` | 참가 인원 | 시작 조건 | AI 동료 |
|---|---:|---|---|
| `solo` | 정확히 1명 | 참가자 1명 준비 | 없음 |
| `coop` | 정확히 3명 | 참가자 3명 전원 준비 | 없음 |

- 협동 Room의 `maxClients`와 정상 시작 인원은 모두 3명이다.
- 솔로와 협동은 서로 다른 매치메이킹 풀을 사용한다.
- 시작 후 신규 사용자의 중도 참가는 허용하지 않고, 기존 사용자의 재접속만 허용한다.
- 클래스 중복 허용 여부는 현재 제한하지 않는다. 제한을 도입할 경우 프로토콜과 로비 UI를 함께 변경한다.

### 2.2 실제 사용자 판정

협동 판정의 `activePlayers`는 서버 상태에서 다음 조건을 모두 만족하는 사용자다.

```text
connected == true AND alive == true
```

- 봇, 관전자, 연결 종료자, 사망·다운 상태 플레이어는 현재 점유 정족수에서 제외한다.
- 단, 협동 Room 자체의 최초 시작 조건은 실제 사용자 3명 준비로 유지한다.
- 연결 종료자를 AI가 대신 조작하지 않는다.

## 3. 서버 권위와 모듈 경계

### 3.1 최종 소유권

| 영역 | 권위 소유자 |
|---|---|
| 로그인·서버 세션·게임 티켓 | Next.js Node + PostgreSQL |
| Room·매치메이킹·재접속 | Colyseus game-server |
| seed·맵·방 연결 | `packages/game-core` |
| 이동 유효성·자동 공격·피해·AI | `packages/game-core`를 호출하는 Colyseus |
| XP·레벨·증강 draft | `packages/game-core`를 호출하는 Colyseus |
| 골드·드롭·장착 | Colyseus + `packages/game-core` |
| 건설(목표) | Colyseus + `packages/game-core`; 현재 서버 판정 미구현 |
| 화면·카메라·사운드·이펙트 | Phaser 클라이언트 |
| HUD·로비·선택 UI | React 클라이언트 |
| 런 결과 | Colyseus가 PostgreSQL transaction으로 저장 |

클라이언트는 HP, 피해, XP, 골드, 드롭 희귀도, 타이머, 승패를 직접 확정하거나 제출하지 않는다.

### 3.2 현재 구조 분석

- Node.js·Colyseus·PostgreSQL, 서버 세션, 90초 game-ticket JWT와 공개 guest route가 구현되어 있다. Cognito 실계정과 공개 배포 운영 검증은 별도다.
- protocol v2는 strict schema, 4KiB/초당30개 제한과 사용자 연결별 공통 단조 증가 `seq`를 사용한다.
- PartyRoom은 solo1/coop3, ready/lock, 20Hz GameCore, 20초 재접속, 최대 35분과 `StateView` 개인 공개 범위를 구현한다. 결과 저장은 동시 호출을 하나의 Promise로 직렬화하고 최대 3회(회당 3초 timeout, 250/750ms backoff)로 제한한다.
- 새 session과 이전 예약 reconnect가 경합하면 새 활성 session을 유지하고 늦게 돌아온 연결을 `DUPLICATE_LOGIN`으로 닫아 player 연결 상태가 잘못 false로 되돌아가지 않게 한다.
- GameCore는 결정론적 3구역 world, room-local 이동, 자동 공격, 정적/히든 반격 AI, 밤 침공, 자원 생산, 정적 리스폰, waypoint·recall, 기본 boss 승패, 개인 drop/equipment와 팀 XP/draft를 실제 시뮬레이션한다.
- PartyRoom은 발견 room/door/enemy/waypoint, 개인 drop/draft와 장비·통계를 Schema에 동기화한다. `structures`는 정의만 있고 비어 있다.
- 현재 실행 scene은 `RoomGameScene`이다. network mode는 server snapshot만 소비하고 로컬 session·이동·전투·AI·경제 tick을 실행하지 않으며 room/player/enemy, owner-only drop, 개인 draft·장비, 팀 통계와 waypoint를 렌더링한다.
- owner-only drop은 `NetworkWorldSnapshot`으로 변환되고 현재 방에 표시된다. 사용자가 drop을 클릭하면 `equipment.equip` 교체 요청을 보내며 750ms 동안 중복 클릭 전송을 막는다.
- 남은 핵심은 network skill/dash/revive, build/structure, 장비 비교·확인·분해 UI와 특수 옵션, 공격·피격 이펙트, 고급 boss pattern, 중앙 봉인 협동 이벤트와 3-client/배포 검증이다.

## 4. 세션 흐름

### 4.1 페이즈

```text
lobby → day → night → standby → day ... → boss → ended
```

| 모드 | 낮 | 밤 | 정비 | 용도 |
|---|---:|---:|---:|---|
| prototype | 60초 | 25초 | 5초 | 반복 검증 |
| full | 210초 | 75초 | 15초 | 정식 흐름 |

- 5일 종료 전 최종 보스를 처치하면 승리한다.
- 제한 시간 종료, 베이스 파괴 또는 정해진 보스전 실패 조건이면 패배한다.
- 보스 진입은 날짜 버튼이 아니라 구역3 게이트와 보스 웨이포인트 조건으로 판정한다.

### 4.2 구역 진행

1. 구역1 시작 방의 베이스캠프에서 시작한다.
2. 방을 탐색하고 자원·정적 몬스터·히든 몬스터 방을 해금한다.
3. 구역 게이트를 파괴하면 끝 웨이포인트가 활성화된다.
4. 파티가 끝 웨이포인트의 이동 조건을 만족하면 다음 구역 시작 방으로 이동한다.
5. 구역3 게이트 파괴 후 같은 방식으로 최종 보스 아레나에 진입한다.

## 5. 절차적 룸맵

### 5.1 좌표와 방 수

- 화면 좌표를 사용하며 y=0이 위쪽이다.
- 시작 방: 좌측 하단 `(0,4)`.
- 게이트 방: 우측 상단 `(4,0)`.
- 구역당 5×5=25칸 중 정확히 15칸을 방으로 사용한다.
- 구역1 시작 방은 우측 `(1,4)`과 상단 `(0,3)`에 고정 통로를 가진다.

### 5.2 방 구성

| 유형 | 구역당 개수 |
|---|---:|
| 시작 방 | 1 |
| 게이트 방 | 1 |
| 자원 방 | 4 |
| 정적 몬스터 방 | 4 |
| 빈 방 | 2 |
| 중앙 웨이포인트 방 | 1 |
| 히든 몬스터 방 | 2 |
| 합계 | 15 |

### 5.3 연결과 깊이

- 시작 방에서 BFS를 수행했을 때 15개 방 모두 도달 가능해야 한다.
- 통로는 상하좌우로 인접한 방 사이에만 생성한다.
- 깊이 점수는 그래프 최단거리 기준으로 계산한다.

```text
depth(room) = dist(start, room) + dist(gate, room)
```

- 시작·게이트를 제외한 깊이 상위 2개 방을 히든 몬스터 방으로 사용한다.
- 동률은 seed 기반 안정 정렬로 결정한다.
- 히든 방은 처음부터 leaf로 생성해 연결 통로 수를 정확히 1개로 유지한다.
- 중앙 웨이포인트 방은 시작·게이트와 맨해튼 거리 1인 칸을 피한다.

### 5.4 멀티플레이 룸 시뮬레이션

확정 기준은 서버가 한 구역의 모든 방을 동시에 시뮬레이션하고, 각 클라이언트는 자기 플레이어가 있는 방을 주 화면으로 렌더링하는 방식이다.

- 플레이어는 서로 다른 방으로 나뉘어 탐색할 수 있다.
- 자동 공격과 일반 적 상호작용은 같은 `roomId` 안에서만 성립한다.
- 다른 방의 파티원은 미니맵·파티 HUD·핑으로 상태를 확인한다.
- 동적 몬스터는 방 그래프 경로를 따라 다음 방으로 이동한다.

## 6. 조작과 자동 공격

### 6.1 입력

- 이동: WASD
- 스킬: Q/E
- 회피: Space
- 귀환: 별도 키 명령
- 증강 선택: 1/2/3
- 마우스: 조준 방향

현재 network mode에서 WASD와 aim은 서버 이동·자동 공격에 사용된다. Q/E/Space button bit는 전송되지만 GameCore가 아직 소비하지 않으므로 스킬과 회피 판정은 **미구현**이다. 로컬 mode의 스킬·회피는 network 판정으로 사용하지 않는다.

### 6.2 자동 공격 대상 선정

서버는 플레이어의 최신 유효 `aim`을 사용한다.

| 공격 방식 | 전체 조준각 | 반각 |
|---|---:|---:|
| 원거리·마법 | 60° | 커서 기준 ±30° |
| 근접 | 110° | 커서 기준 ±55° |

대상 선정 순서:

1. 공격자와 같은 방이며 살아 있는 적만 남긴다.
2. `distance <= attackRange`인 적만 남긴다.
3. 공격 종류별 조준 원뿔 안의 적만 남긴다.
4. 거리가 가장 짧은 적을 선택한다.
5. 거리가 같으면 안정적인 network ID 오름차순으로 결정한다.
6. 대상이 없으면 공격 주기를 소비하지 않는다.

기본 자동 공격의 대상·주기·피해·처치·XP는 서버가 계산한다. network mode는 서버 enemy/HP를 렌더링하며 로컬 공격을 실행하지 않는다. 투사체·피격 이펙트와 일부 고급 증강 효과는 아직 표현/판정이 완성되지 않았다.

### 6.3 조준 커서

- 전투 화면의 기본 OS 커서를 중세 판타지풍 조준점으로 교체한다.
- 건설·메뉴 UI 위에서는 일반 포인터를 사용할 수 있다.
- 조준점은 배경 명도와 무관하게 식별되도록 외곽선과 중심점을 가진다.

## 7. 몬스터

### 7.1 정적 몬스터

```text
idle → provoked → returning → idle
             └→ dead → respawn
```

- 플레이어에게 피해를 받기 전에는 선공하지 않는다.
- 피격 후에만 공격자를 추적한다.
- 생성 방 밖으로 나갈 수 없다.
- 목표가 사망하거나 생성 방을 벗어나면 원위치로 돌아간다.
- 사망 후 prototype 30초, full 90초 뒤 같은 생성 방에서 리스폰한다.
- 리스폰 시 HP와 상태를 초기화한다.

### 7.2 동적 몬스터

- 활성 게이트에서 생성된다.
- 방 그래프를 따라 해당 구역 시작 웨이포인트를 경유해 구역1 베이스로 이동한다.
- 플레이어를 발견하거나 피격돼도 플레이어를 target으로 설정하지 않는다.
- 최종 목표는 베이스이며 도달 후 베이스를 공격한다.
- 플레이어와의 접촉 피해 여부는 별도 밸런스 결정 전까지 사용하지 않는다.

### 7.3 히든 몬스터

- 구역당 2개 히든 방에 배치한다.
- 일반 정적 몬스터보다 높은 체력·피해·사거리를 사용하고 피격 후 반격한다.
- 고유 투사체/원거리 패턴 표현은 아직 미구현이다.
- 처치 시 런에 등록된 각 플레이어의 개인 장비를 결정론적으로 생성한다.

## 8. 자원·경제·건설

### 8.1 자원 방

- 최초 진입 시 영구 해금한다.
- 해금된 자원 방 하나당 팀 골드 `+1`을 5초마다 생산한다.
- 최대 생산량은 구역 3개 기준 자원 방 12개, 즉 5초당 12골드다.
- 생산은 서버 시계로 처리하며 클라이언트 비활성화나 방 체류 여부에 영향받지 않는다.
- 중복 해금과 중복 tick으로 골드가 두 번 지급되지 않아야 한다.

### 8.2 건설 UI와 검증 — 미구현

- network HUD는 `buildSupported=false`로 건설 미지원을 표시한다.
- `build.place`와 `build.upgrade` schema는 존재하지만 PartyRoom은 `BUILD_NOT_READY`로 거부하고 `structures`는 비어 있다.
- 로컬 mode의 포탑·장벽은 기능 시연용이며 network mode의 대체 판정이 아니다.
- 후속 서버 구현은 비용, 좌표, 점유, 최대 레벨, 충돌과 경로 차단을 한 명령 transaction 안에서 검증해야 한다.

## 9. 웨이포인트·귀환·보스 진입

### 9.1 웨이포인트

구역당 세 종류를 사용한다.

1. 시작 웨이포인트: 시작부터 활성
2. 중앙 웨이포인트: 해당 방 발견 후 활성
3. 끝 웨이포인트: 게이트 파괴 후 활성

### 9.2 5초 점유 규칙

- 이동 요청 시 출발 웨이포인트 위에 `activePlayers` 전원이 있어야 한다.
- 조건이 유지되는 동안 서버가 5,000ms를 누적한다.
- 한 명이라도 범위를 벗어나거나 사망·연결 종료되면 카운트다운을 0으로 초기화하고 새 정족수로 다시 판정한다.
- 솔로도 동일하게 5초를 기다린다.
- 진행률은 `holdingPlayers`, `requiredPlayers`, `holdProgress`, `holdDurationMs`로 동기화한다.
- 목적지는 활성화된 웨이포인트 또는 베이스만 선택할 수 있다.

이 규칙은 GameCore·PartyRoom·Schema·RoomGameScene HUD까지 연결되어 있다.

### 9.3 귀환

- `recall.request`는 현재 활성 waypoint 위에서만 시작할 수 있다.
- 이동과 같은 `connected && alive` 전원 정족수와 5초 점유를 재사용한다.
- 완료하면 활성화된 구역1 시작 waypoint로 이동한다.
- boss phase에서는 귀환을 거부한다.

### 9.4 최종 보스

- 구역3 게이트가 파괴되기 전에는 보스 웨이포인트를 활성화하지 않는다.
- 보스 입장도 일반 이동과 동일한 전원 5초 점유 규칙을 사용한다.
- 클라이언트의 버튼 표시 여부만으로 입장을 승인하지 않는다.
- 격리 boss room, 기본 HP, 서버 자동 공격에 의한 피해와 처치 승리는 구현되어 있다.
- 보스의 탄막·장판·소환·광폭화와 플레이어 대상 공격은 미구현이다.

## 10. 장비

### 10.1 슬롯과 희귀도

| 슬롯 | 제공 스탯 |
|---|---|
| weapon | 공격력 |
| armor | 최대 체력 + 방어력 |
| accessory | 공격속도 |

| 희귀도 | 기본 스탯 배율 | 특수 옵션 수 |
|---|---:|---:|
| normal | 20% | 0 |
| rare | 40% | 0 |
| epic | 60% | 1 |
| legendary | 80% | 0 |
| mythic | 100% | 2 |

레전더리는 에픽보다 기본 스탯이 높지만 특수 옵션은 없다. 이 규칙은 의도된 차별점이다.

### 10.2 개인 히든 드롭

- 히든 몬스터 처치 시 적격 플레이어마다 개인 장비 1개를 생성한다.
- 희귀도: Legendary 80%, Mythic 20%.
- 슬롯은 weapon/armor/accessory 중 seed 기반으로 결정한다.
- seed에는 run seed, zone, hidden room ID, player ID, drop index를 포함한다.
- 파티원 배열 순서가 달라도 같은 플레이어의 결과는 변하지 않는다.
- 다른 플레이어는 개인 드롭을 장착하거나 수령할 수 없다.
- 드롭 ID 중복 수령과 이중 장착을 서버가 차단한다.

### 10.3 현재 적용과 남은 장비 결정

GameCore는 100% 기준 weapon 공격력 +20, armor 최대 HP +80/방어 +8, accessory 공격속도 +30%를 임시 서버값으로 적용한다. 더 높은 `equipmentPower`의 아이템은 자동 장착하고, 그렇지 않은 아이템은 소유자 전용 drop state로 남긴다. 장비 효과와 소유권 기반 `equipment.equip`은 서버에 연결되어 있다.

owner-only drop의 transport/장면 표시와 클릭 교체 요청, 750ms 중복 방지는 구현됐다. 현재 남은 범위는 장비 비교·확인·분해 UI, 특수 옵션 효과 풀, 사망 시 장비 처리와 일반 몬스터 드롭이다. 기본 스탯 수치는 작동 중인 임시값이며 밸런스 승인 대기다.

## 11. 레벨·XP·증강

### 11.1 레벨

- 시작 레벨 1, 최대 레벨 30.
- 다음 레벨 요구 XP는 `14 + 현재 레벨 × 9`다.
- 한 번의 XP 지급으로 여러 레벨을 넘을 수 있다.
- 레벨 30 도달 후 추가 XP는 레벨을 올리지 않는다.
- 팀 XP와 팀 레벨은 공유하고, 증강 선택과 장비는 플레이어별로 관리한다.

### 11.2 증강 draft

- 10/20/30은 해당 클래스의 전직 증강만 제시한다.
- 나머지 레벨은 공격 관련 공용 증강만 제시한다.
- 각 draft는 중복 없는 정확히 3개 선택지다.
- run seed, player ID, 클래스, 레벨, draft index, 현재 stack을 seed에 포함한다.
- 멀티플레이 중 게임을 일시정지하지 않는다.
- `vitality`, `armor`, `mobility`는 후보와 타입에서 제거한다.
- 일반 증강은 총 37 stack 용량을 가져 26회의 비전직 선택을 수용한다.
- 클래스마다 최대 중첩 1의 전직 증강 5개를 보유해 세 번의 전직에서 항상 3개 후보를 제공한다.

### 11.3 선택 UI

- 화면 하단의 소형 패널로 표시한다.
- 캐릭터와 전투 중심 영역을 가리지 않는다.
- 클릭과 1/2/3 키를 모두 지원한다.
- 서버가 발급한 현재 `draftId`와 포함된 `upgradeId`만 승인한다.

## 12. 협동 콘텐츠

현재 network mode에서 동작하는 협동 축은 다음과 같다.

1. 웨이포인트·보스 진입의 전원 5초 점유
2. 분산 탐색과 공유 자원 생산
3. 밤 침공 적의 공유 베이스 HP 공격

건설 투자는 서버 건설 구현 뒤 이 축에 추가한다. 추가 협동 장치의 우선 제안은 중앙 웨이포인트 방의 인원 비례 봉인 발판이다. `activePlayers`가 각 발판을 5초 점유하면 중앙 웨이포인트와 팀 보상을 활성화한다. 이 기능은 현재 **미구현/결정 필요**이며 방 유형 수를 늘리지 않고 중앙 웨이포인트 방에 포함한다.

## 13. 프로토콜 v2 계약 요약

모든 클라이언트 명령은 다음 envelope를 사용한다.

```ts
{
  v: 2,
  seq: number,
  clientTime: number,
  type: string,
  payload: object
}
```

| 명령 | 목적 | 현재 단계 |
|---|---|---|
| `room.ready` | 로비 준비 | 서버 의미 처리 구현 |
| `player.input` | 이동축·조준·버튼 | 이동·aim 구현, Q/E/Space 미소비 |
| `skill.cast` | Q/E 스킬 의도 | schema만 존재, `SKILL_NOT_READY` |
| `player.interact` | 문·drop·waypoint 상호작용 | 서버 의미 처리 구현 |
| `travel.request` | 웨이포인트 이동 요청 | 정족수·목적지·5초 이동 구현 |
| `recall.request` | 별도 귀환 요청 | 활성 waypoint·전원 5초 귀환 구현 |
| `upgrade.choose` | 개인 draft 선택 | draft ID·선택지 검증과 효과 적용 구현 |
| `equipment.equip` | 개인 드롭 장착 | 소유자·room·미수령 검증과 효과 적용 구현 |
| `build.place` | 시설 배치 | schema만 존재, `BUILD_NOT_READY` |
| `build.upgrade` | 시설 강화 | schema만 존재, `BUILD_NOT_READY` |

- 모든 명령은 strict schema, protocol version, 4KiB 메시지 크기, 초당30개 제한과 사용자 연결별 공통 단조 증가 `seq`를 통과한다.
- drop·draft·waypoint·door의 현재 구현 범위에서 존재·소유권·room/목적지 조건을 검증한다.
- 스킬·건설은 묵시적으로 성공시키지 않고 준비 전 오류를 반환한다.

## 14. 저장과 공개 테스트

### 14.1 PostgreSQL

- 사용자, 서버 세션, 방명록, match, match_players를 저장한다.
- 실시간 위치·탄막·AI tick은 DB에 저장하지 않는다.
- 결과는 Room 종료 시 한 transaction으로 한 번만 저장한다. 프로세스 안에서는 중복 finalize를 직렬화하고 3회 bounded retry 후에도 실패하면 오류를 기록한 뒤 Room 종료를 계속한다. crash-safe 보장은 durable outbox 도입 전까지 제공하지 않는다.
- 0.2 장비는 우선 런 내부 상태이며 영구 보관 여부는 별도 결정한다.

### 14.2 공개 접근

공개 guest session route가 구현되어 있다. 비운영 환경에서는 guest 접근을 허용하고, production에서는 `PUBLIC_PLAYTEST_ENABLED=true`일 때만 guest session을 발급한다. guest도 PostgreSQL 사용자·세션과 game-ticket 경로를 거친다. Google/Cognito를 필수로 할지는 구현 차단 사유가 아니라 배포 정책 선택이다.

공개 배포 전 남은 보강은 guest/IP rate limit, 만료 row 정리·보존 기간과 실제 악용 테스트다.

- [남음] 다른 사용자의 private `StateView`가 draft/drop을 받지 않는 다중 client test

### 16.2 수동/E2E

- 세 브라우저가 같은 맵·방·HP·골드·웨이포인트 진행률을 본다.
- 세 사용자가 다른 방에 있어도 각자 화면과 미니맵이 정상이다.
- 한 사용자가 점유 범위를 벗어나면 세 화면의 5초 진행률이 즉시 초기화된다.
- 금지된 로컬 값 변조로 피해·골드·드롭·보스 입장을 만들 수 없다.
- 증강 UI가 전투 화면 하단에 표시되고 1/2/3으로 선택된다.
- network HUD는 건설 미지원 상태를 표시하고 로컬 건설 판정을 실행하지 않는다.
- 스킬·부활·건설·고급 boss pattern 구현 후 해당 판정과 표현을 별도로 검증한다.

미결정: 플레이어가 있는 방만 full tick하고 빈 방은 저주기 tick할지 여부.

### 17.5 공개 인증

| 대안 | 장점 | 단점 | 상태 |
|---|---|---|---|
| 익명 게스트 세션 + 단기 game-ticket | 링크 즉시 테스트 | 악용 방지·식별 정책 필요 | **현재 구현** |
| Google/Cognito 로그인 필수 | 기존 보안·전적 연계 | 테스트 진입 마찰 | 현재 기반 |
| 초대 코드 + 게스트 세션 | 제한 공개 용이 | 코드 관리 필요 | 후보 |

기본 공개 테스트 경로는 guest로 구현됐다. 최종 공개 배포에서는 guest를 계속 열지, Google/Cognito 또는 초대 코드로 제한할지를 운영 정책으로 선택한다. 어느 경우든 guest rate limit·cleanup 검증은 필요하다.

### 17.6 추가 미결정

- 서버 클래스·베이스 수치: `CLASS_COMBAT_RULES`와 현재 장비 기준값이 실행 원본이며 최종 밸런스 승인은 대기다.
- 귀환: 활성 waypoint에서 연결·생존 사용자 전원 5초 점유 후 zone1 base로 이동하는 방식이 현재 구현값이다.
- 공격속도: `interval / (1 + 증강 보너스 + 장비 보너스)`가 현재 구현식이며 최소 주기는 0.12초다.
- 중앙 협동 콘텐츠: 봉인 발판, 게이트 채널링, 호위 이벤트 중 선택 필요.
- 정적 몬스터는 리스폰 시 방 `cleared=false`가 되고 재처치 XP·골드를 다시 지급한다. 변경 여부는 밸런스 승인 대상이다.

## 18. 0.2 Definition of Done

현재 충족: 3구역 맵, 기본 이동·자동 공격·AI·경제·XP/draft·장비·waypoint/recall·기본 boss, snapshot-only network scene과 공개 guest route.

릴리스 완료에 남은 조건:

- network skill/dash/revive와 build/structure를 서버가 확정한다.
- 장비 비교·확인·분해 UI와 특수 옵션, 공격·피격 이펙트, 고급 boss pattern을 client/server 계약에 연결한다.
- 중앙 봉인 협동 이벤트를 확정·구현하거나 0.2 범위에서 명시적으로 제외한다.
- 실제 세 브라우저에서 room 분산·waypoint·reconnect·StateView privacy·결과 저장 E2E를 통과한다.
- 공개 guest abuse rate limit/cleanup을 적용하고 배포 URL 신규 사용자 완주 smoke test를 통과한다.
