# 《5일 뒤 마왕》 3인 개발 협업 역할분담 보고서

> 문서 버전: v1.0
> 대상: 시스템 기획 / 레벨 디자인 기획 / 백엔드(서버)
> 기준 자료: 게임 고도화 기획서, 프로토타입 제안서, 현재 웹 프로토타입 구조
> 협업 목표: 3인이 병렬로 작업하되, 데이터와 인터페이스 충돌을 최소화하며 플레이 가능한 수직 슬라이스를 확장
## 1. 협업 결론

세 역할은 다음 순서로 맞물린다.

```text
시스템 기획 ── 밸런스·경제·성장 데이터 ──┐
                                           ├─ 공통 데이터 계약 → 백엔드 검증·동기화
레벨 디자인 ── 맵 시드·방·웨이브 배치 ──────┘
                                           ↓
                                   클라이언트 게임 런타임
```

- **시스템 기획 담당**은 전투·성장·경제의 규칙과 수치의 단일 소유자다.
- **레벨 디자인 담당**은 공간 진행, 방 템플릿, 게이트·웨이브의 배치와 플레이테스트를 소유한다.
- **백엔드 담당**은 룸 생명주기, 서버 권위 판정, 인증·저장·배포를 소유한다.
- 세 담당자는 코드보다 먼저 `공통 데이터 계약`과 `변경 로그`를 합의한다.

## 2. 개발 목표와 공통 완료 기준

### 2.1 이번 스프린트의 목표

1. 3인이 같은 게임 룸에 들어올 수 있다.
2. 낮에는 구역을 탐험하고 밤에는 베이스를 방어한다.
3. 공유 경험치·골드, 개인 빌드 선택, 시설 투자가 실제 전투력 차이를 만든다.
4. 3구역 게이트를 지나 마왕방에 입장하고 승패가 확정된다.
5. 런 결과와 기여도, 방명록을 저장한다.

### 2.2 공통 수용 기준

- 3인 기준 전체 런이 정식 모드 25분 안에 종료된다.
- 개발용 단축 모드에서 동일한 상태 전이를 10분 이내 반복 검증할 수 있다.
- 같은 시드와 같은 입력은 같은 방 배치·웨이브·드롭 결과를 만든다.
- 서버와 클라이언트가 같은 데이터 ID를 사용하며 수치를 중복 정의하지 않는다.
- 1·2인 접속도 가능하고 인원 감소 보정이 적용된다.
- 변경 사항은 담당자가 PR 또는 변경 로그에 목적·영향 범위·테스트 결과를 남긴다.

## 3. 역할 A — 시스템 기획(밸런스·경제·성장)

### 3.1 핵심 책임

- 클래스 3종의 전투 리듬과 조작 난이도 설계
- 자동 평타, Q/E 스킬, 회피의 피해·쿨다운·사거리 밸런스
- 공유 경험치·골드, 건설 비용, 사망 손실, 보상 곡선 설계
- 레벨업 선택지·3/6/9레벨 전직 분기 설계
- 장비 슬롯·희귀도·전용 옵션·드롭 보정 설계
- 인원별 난이도 보정과 이지/노말/하드 난이도 기준 수립
- 결과 화면의 기여도 지표와 메타 해금 보상 정의

### 3.2 소유 데이터

```text
src/game/content/classes.ts
src/game/content/upgrades.ts
src/game/content/balance.ts
```

향후 확장 파일:

```text
src/game/content/items.ts
src/game/content/enemies.ts
src/game/content/buildings.ts
src/game/content/waves.ts
```

수치 변경은 가능하면 위 데이터 파일에서 끝나야 하며, 런타임 로직을 직접 수정하는 방식은 피한다.

### 3.3 필수 산출물

| 산출물 | 내용 | 완료 기준 |
|---|---|---|
| 클래스 시트 | 체력·공격·방어·속도·사거리·평타·Q/E | 3종의 차이가 60초 안에 체감됨 |
| 성장 테이블 | 레벨별 XP, 선택지, 전직 분기 | 레벨업 후보 2~3개, 클래스 전용 조건 검증 |
| 장비 테이블 | 슬롯·희귀도·스탯·전용 옵션 | 클래스 전용 무기 경쟁 방지 |
| 경제 테이블 | 골드 수급·건설·업그레이드·소모품 | 한 런에서 투자 우선순위가 발생 |
| 인원 보정표 | 1/2/3인 적 HP·스폰·보스·XP | 인원별 보스 도달 가능성 유지 |
| 밸런스 리포트 | 테스트 시드별 결과, 문제, 조정안 | 조정 전후 근거 포함 |

### 3.4 주요 수치의 시작값

| 항목 | 1인 | 2인 | 3인 |
|---|---:|---:|---:|
| 일반 적 HP | ×0.55 | ×0.75 | ×1.00 |
| 밤 스폰 수 | ×0.50 | ×0.75 | ×1.00 |
| 보스 HP | ×0.50 | ×0.75 | ×1.00 |
| XP 요구량 | ×0.80 | ×0.90 | ×1.00 |
| 사망 시 공용 골드 손실 | 15% | 15% | 15% |

시작값은 정답이 아니라 플레이테스트 기준선이다. 1회 조정에서 두 개 이상의 축을 동시에 변경하지 않는다.

### 3.5 시스템 담당의 플레이테스트

- 30초 허수아비 DPS와 3개 클래스 실전 처치 시간 비교
- 1일차 밤에 포탑 1레벨만으로 방어되는지 확인
- 3일차에 빌드 방향이 명확히 갈리는지 확인
- 레어 장비·전직 직후 전투력이 25~45% 상승하는지 확인
- 좋은 장비를 얻은 1인이 캐리할 수 있지만, 소환 게이트·시설 방어에서 팀이 여전히 필요한지 확인

## 4. 역할 B — 레벨 디자인 기획(맵·방·웨이브)

### 4.1 핵심 책임

- 베이스 → 1구역 → 2구역 → 3구역 → 보스방의 공간 진행 설계
- 구역별 테마·위험도·보상·시야·전투 거리 설계
- 전투방·게이트방·자원방·히든방·웨이포인트방 템플릿 제작
- 필수 경로와 선택 경로의 분기, 랜덤 배치 안전장치 설계
- 낮 탐험과 밤 기지 방어의 이동 압박 설계
- 게이트 진입 방향, 동적 몬스터 경로, 시설 방어 구역 설계
- 보스 아레나의 탄막 안전지대와 소환 게이트 위치 설계

### 4.2 소유 데이터

권장 폴더:

```text
src/game/content/levels/
├─ zones.ts
├─ roomTemplates.ts
├─ mapSeeds.ts
├─ waveRoutes.ts
└─ bossArena.ts
```

현재 고정 좌표는 `src/game/content/balance.ts`에 있으므로, 맵 확장 시 레벨 데이터로 분리한다. 시스템 담당의 적·보상 ID를 참조하고 수치 자체는 복제하지 않는다.

### 4.3 필수 산출물

| 산출물 | 내용 | 완료 기준 |
|---|---|---|
| 월드 흐름도 | 구역·게이트·웨이포인트·보스 진입 | 베이스에서 보스까지 항상 유효 경로 존재 |
| 방 템플릿 | 전투·자원·히든·이벤트 방 | 방당 목표·입구·출구·위험 요소 명시 |
| 시드 규칙 | 랜덤 조합과 필수 방 보장 | 성장 불가능한 불합리 시드 차단 |
| 웨이브 표 | 일차·페이즈·진입로·적 조합 | 낮/밤 역할 차이가 발생 |
| 보스 아레나 도면 | 패턴·안전지대·소환 위치 | 3패턴 예고와 판정 일치 |
| 레벨 테스트 보고서 | 길찾기·시야·이동 시간·사망 위치 | 문제 좌표와 재현 시드 포함 |

### 4.4 공간 설계 체크리스트

- 베이스에서 첫 게이트까지 1일차 낮의 절반 안에 도달할 수 있는가?
- 밤 시작 전 귀환과 잔류 중 어느 선택도 상황에 따라 유효한가?
- 서로 다른 방에 있는 팀원이 미니맵과 핑만으로 위험을 이해할 수 있는가?
- 히든방은 강한 보상을 주지만 필수 경로를 막지 않는가?
- 장벽이 모든 적을 영구적으로 막는 배치가 되지 않는가?
- 3구역은 보상 상승을 체감시키되 신규 플레이어가 진입 자체를 포기하지 않는가?

## 5. 역할 C — 백엔드(서버·인증·저장)

### 5.1 핵심 책임

- 3인 룸 생성·참가·퇴장·재접속 정책
- 서버 권위 타이머, 페이즈, 적 스폰, 피해, 드롭, 골드, 건설 판정
- `GameCommand` 입력 검증과 `GameSnapshot` 동기화
- 인원 감소 보정과 방장·투표 상태 관리
- 로그인 사용자 식별, 방명록·런 결과 저장
- D1/PostgreSQL 마이그레이션, 운영 로그, 배포 환경 관리
- 치팅·중복 구매·이중 드롭·클라이언트 변조 방지

### 5.2 현재 구현과 확장 경계

현재 프로토타입은 다음 구조를 사용한다.

```text
src/game/transport/GameTransport.ts  # 교체 가능한 계약
src/game/transport/LocalTransport.ts # 현재 기본 구현
src/game/runtime/GameBridge.ts       # 명령·스냅숏 경계
app/api/guestbook/route.ts            # 방명록 API
app/api/runs/route.ts                 # 런 결과 API
db/schema.ts                          # D1 스키마
```

실제 멀티플레이 단계에서는 `WebSocketTransport` 또는 별도 `apps/game-server`를 추가하고, 서버가 아래 상태를 소유한다.

- 일차·페이즈 타이머
- 플레이어 위치 검증과 충돌
- 적 AI·피해·사망·부활
- 경험치·레벨·특성 선택
- 골드·드롭·공용 인벤토리
- 시설 비용·위치·내구도·업그레이드
- 보스 투표·후퇴·승패

### 5.3 필수 산출물

| 산출물 | 내용 | 완료 기준 |
|---|---|---|
| 프로토콜 문서 | 명령·이벤트·스냅숏 필드와 타입 | 프론트와 동일 ID·enum 사용 |
| 룸 상태기계 | 생성·준비·진행·종료·재접속 | 중복 룸·유령 플레이어 방지 |
| 인증 API | 사용자 식별·권한·실패 응답 | 서버에서 사용자 확인 |
| 저장 스키마 | 프로필·방명록·런 결과·인덱스 | 마이그레이션 재현 가능 |
| 부하·지연 테스트 | 1/2/3인, 지연·재접속·동시 구매 | 중복 차감과 상태 유실 없음 |
| 배포 런북 | 환경변수·DB·롤백·로그 확인법 | 다른 팀원이 재배포 가능 |

### 5.4 서버 테스트 우선순위

1. 같은 골드에 두 번 구매 요청을 보내도 한 번만 차감
2. 같은 드롭 ID를 두 번 수령해도 아이템 복제 불가
3. 클라이언트 타이머를 조작해도 서버 페이즈가 변하지 않음
4. 보스 투표 과반수·취소·1회 후퇴가 정확히 동작
5. 1·2·3인 보정값이 룸 시작 시 고정되고 중간 변경되지 않음
6. 방명록 입력 길이·HTML·인증 오류를 서버에서 차단

## 6. 공통 인터페이스와 파일 규칙

### 6.1 단일 데이터 원칙

- ID는 `lower-kebab-case`를 사용한다. 예: `mage-nova`, `zone-forest-gate`.
- 표시명은 UI에서만 정의하고 게임 로직은 ID를 사용한다.
- 수치 단위는 문서에 명시한다. 시간은 초, 쿨다운은 ms, 피해·체력·골드는 정수다.
- 랜덤 결과는 `seed`, `tableId`, `rollIndex`를 기록해 재현 가능하게 한다.
- 삭제보다 `deprecated: true`를 우선해 과거 런 재현을 보장한다.

### 6.2 변경 영향표

| 변경 | 시스템 | 레벨 | 백엔드 | 필수 확인 |
|---|---|---|---|---|
| 적 HP/피해 | 작성 | 참조 | 검증 | 전투·웨이브 테스트 |
| 방 연결·좌표 | 참조 | 작성 | 동기화 | 길찾기·시드 테스트 |
| 새 스킬 | 작성 | 이펙트 위치 제공 | 명령 검증 | 쿨다운·피해 이벤트 |
| 새 시설 | 비용·효과 작성 | 배치 위치 제공 | 구매·내구도 검증 | 동시 구매 테스트 |
| 새 드롭 | 희귀도·옵션 작성 | 드롭 방 배치 | 중복 수령 방지 | 시드·불운 보정 |
| 페이즈 시간 | 기준 합의 | 웨이브 배치 | 서버 타이머 | 5일 상태기계 |

### 6.3 PR·커밋 규칙

- 커밋 제목: `feat(system):`, `feat(level):`, `feat(server):`, `fix:`, `docs:`
- 한 PR은 한 역할의 한 목적만 포함한다.
- PR 본문에 `변경 목적 / 영향 파일 / 검증 방법 / 남은 리스크`를 작성한다.
- 공통 타입이나 데이터 ID 변경은 관련 담당자 2명 이상 리뷰 후 병합한다.
- 밸런스 수치만 바꾸는 PR도 재현 시드와 전후 결과를 첨부한다.

## 7. 3일 작업 분배안

### 1일차 — 계약과 수직 슬라이스

| 시스템 기획 | 레벨 디자인 | 백엔드 |
|---|---|---|
| 클래스·적·시설 시작값 확정 | 베이스·3구역 연결 도면 | 룸·사용자 상태 초안 |
| XP·골드·사망 손실 표 | 방 템플릿 4종 | `GameCommand`/`Snapshot` 계약 |
| 테스트 케이스 작성 | 게이트·웨이포인트 좌표 | 인증·DB 마이그레이션 초안 |

**공동 결과:** 한 명이 이동·공격하고 서버 또는 로컬 룸에서 적 1종을 처치하는 최소 루프.

### 2일차 — 낮/밤과 성장

| 시스템 기획 | 레벨 디자인 | 백엔드 |
|---|---|---|
| 레벨업·전직·장비 드롭 추가 | 방 연결 랜덤 규칙 | 페이즈·웨이브 권위 처리 |
| 1/2/3인 보정 적용 | 밤 진입로·시설 방어선 | 골드·건설·피해 검증 |
| 3일차까지 밸런스 플레이 | 히든방·보상 배치 | 방명록·런 결과 API |

**공동 결과:** 3인이 낮에 탐험하고 밤에 베이스를 지키며 성장 선택을 하는 한 런.

### 3일차 — 보스와 안정화

| 시스템 기획 | 레벨 디자인 | 백엔드 |
|---|---|---|
| 보스 요구 전투력·결과 지표 | 보스 아레나·패턴 안전지대 | 보스 투표·후퇴·승패 |
| 기여도·메타 보상 | 시드별 길막·난이도 검증 | 재접속·동시 요청 테스트 |
| 난이도 최종 조정 | 플레이테스트 리포트 | 배포·롤백 런북 |

**공동 결과:** 정식 25분 모드 3회와 단축 모드 반복 테스트를 통과한 배포 후보.

## 8. 협업 의사결정 규칙

- **수치 충돌:** 시스템 기획 담당이 초안을 제시하고 백엔드 담당이 검증 비용, 레벨 담당이 플레이 영향 의견을 낸 뒤 합의한다.
- **맵 충돌:** 레벨 디자인 담당이 공간 목적과 우회 경로를 지키고 시스템 담당이 보상·전투 요구량을 조정한다.
- **네트워크 충돌:** 백엔드 담당이 서버 권위와 보안 기준을 지키되, 플레이 감각에 영향을 주는 지연 보정은 세 역할이 함께 테스트한다.
- 30분 안에 결론이 나지 않는 변경은 현재 값으로 고정하고, `open-issue`에 대안과 결정 기한을 남긴다.
- 발표 직전에는 새 콘텐츠보다 버그·재현성·세션 완주율을 우선한다.

## 10. 최종 역할별 Definition of Done

### 시스템 기획

- 클래스·성장·장비·경제 테이블이 데이터 파일로 존재한다.
- 단축 모드와 정식 모드의 기대 성장 곡선이 문서화되어 있다.
- 세 클래스, 시설, 보스의 최소 수치 테스트가 통과한다.
- 변경 전후의 플레이 결과가 기록되어 있다.

### 레벨 디자인

- 필수 경로·웨이포인트·히든방·보스 진입 조건이 모든 시드에서 보장된다.
- 낮 탐험과 밤 방어의 이동·시야·보상 차이가 플레이로 확인된다.
- 장벽·게이트·웨이브가 기지를 무적 또는 불가피한 패배로 만들지 않는다.
- 보스 아레나 패턴 예고와 안전지대가 재현된다.

### 백엔드

- 3인 룸에서 서버 권위 시간·피해·경제·승패가 유지된다.
- 인증 사용자만 사용자 소유 데이터에 접근한다.
- 방명록·런 결과 마이그레이션과 API가 배포 환경에서 동작한다.
- 지연·재접속·중복 요청·악성 입력 테스트 결과가 남아 있다.
